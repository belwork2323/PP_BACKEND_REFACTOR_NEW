QC DIVISION MASTER AND AUTO-POPULATE APIs
=========================================

The division master is stored in MongoDB. API consumers use numeric division
IDs; display names are returned from the master collection. These APIs are
read-only and do not create or update a QC form.

Base URL: /api/v1/user/qc-division
Authorization: User


1. FETCH ALL QC DIVISIONS
=========================

Method: GET
URL: /api/v1/user/qc-division/divisions
Request body: none

Success response: 200 OK

{
  "success": true,
  "code": 200,
  "message": "QC divisions fetched successfully",
  "data": [
    {
      "divisionId": 1,
      "divisionName": "Raw Material",
      "disabled": false,
      "types": [
        {
          "divisionId": 101,
          "divisionName": "Raw Material Revalidation",
          "disabled": false
        },
        {
          "divisionId": 102,
          "divisionName": "Raw Material Processing",
          "disabled": false
        }
      ]
    },
    {
      "divisionId": 2,
      "divisionName": "Mixing",
      "disabled": false,
      "types": []
    },
    {
      "divisionId": 12,
      "divisionName": "Static Test Facility",
      "disabled": true,
      "types": []
    }
  ],
  "timestamp": "2026-08-05T12:00:00"
}

Rules:

- Top-level divisions are returned by displayOrder.
- Nested types are also returned by displayOrder.
- Disabled divisions remain in the response so the UI can display them.
- Numeric IDs are unique across both top-level divisions and nested types.


2. AUTO-POPULATE SELECTED QC DIVISION
=====================================

Method: POST
URL: /api/v1/user/qc-division/division-details
Content-Type: application/json

Request body:

{
  "batchId": "BATCH-2026-0001",
  "divisionId": 101
}

Request fields:

  batchId
    Type: string
    Required: yes
    Description: Active batch whose identification-sheet materials are loaded.

  divisionId
    Type: number
    Required: yes
    Supported values:
      101 - Raw Material Revalidation
      102 - Raw Material Processing
      2   - Mixing
      3   - Hardware
      4   - Casting
      5   - Curing
      6   - De-coring
      7   - Trimming
      8   - Post Cure
      9   - NDT
    Description: Numeric ID of the final selectable division/type.

Response rules:

  raw-material sourcing lot-details logic.
- grade is omitted when neither the lot nor identification-sheet material has a
  grade.
- progressInsights, qualityInsights and workflowInsights are not returned.
- The endpoint does not save the populated data or create a QC form.

Casting and Curing rules:

SILENT SOURCE-DATA FALLBACK
===========================

This endpoint is called silently by the UI. After the batch and selected
division have been validated, a missing source record returns 200 OK instead
of propagating a 404. The selected division and batch are still returned, and
the division-specific collection is empty:

- Raw Material Revalidation: "materials": []
- Raw Material Processing: "premixes": []
- Mixing: "stages": []
- Hardware: "motors": []
- Casting: "motors": []
- Curing: "motors": []
- De-coring: "motors": []
- Trimming: "motors": []
- Post Cure: "motors": []
- NDT: "motors": []

This applies to missing forms, lots, and other source-detail records. Unknown
division IDs and missing/deleted batch IDs remain errors because the request
itself cannot be resolved.

QC DIVISION-WISE APPROVER API
============================

WHAT CHANGED
============

- The existing division change-status endpoint now supports division-level,
  premix-level, and motor-level QC approvals.
- Every QC approval request must pass divisionId and division. Both values are
  validated against the workflow stored for the QC form.
- For Raw Material approvals, division can be RAW_MATERIAL with subType
  RAW_MATERIAL_REVALIDATION/RAW_MATERIAL_PROCESSING, matching the saved form
  payload. The canonical subtype name is also accepted as division.
- Raw Material Revalidation and Weightment are approved at division level and
  do not require premixNo or motorId.
- Raw Material Processing requires premixNo.
- Mixing requires premixNo and stageType because PREMIX 1 and FINAL_MIX 1 are
  separate approval units.
- Motor-based divisions require motorId.
- The existing premix and motor change-status endpoints are retained. When
  those endpoints are used for a QC Division form, divisionId and division
  must also be passed.
- The unified endpoint always returns QcDivisionFormResponse and identifies
  the acted-on division and unit.


UNIFIED APPROVER ENDPOINT
=========================

Method: POST
URL: /api/v1/approver/form/division/change-status
Authority: Approver
Content-Type: application/json

COMMON REQUEST FIELDS
=====================

Field             Type       Required       Description
----------------  ---------  -------------  ---------------------------------
formId            String     Yes            QC Division form ID.
subDepartmentId   Long       Yes            Must match the saved QC form.
divisionId        Long       Yes            QC division/type ID.
division          String     Yes            Canonical API division name.
actionType        Status     Yes            APPROVED or REJECTED.
remarks           String     No             Approval remarks.
rejectionReason   String     For rejection  Required for REJECTED.
subType           String     Conditional    Saved division subtype.
premixNo          Integer    Conditional    Required for premix divisions.
motorId           String     Conditional    Required for motor divisions.
stageType         StageType  Conditional    Required for MIXING; PREMIX or
                                             FINAL_MIX.

premixNo and motorId must not be sent together.

COMMON UNIFIED RESPONSE FIELDS
==============================

QcDivisionFormResponse can contain:

- formId, batchId, subDepartmentId, formSubmissionType, status
- divisionId, division, subType
- motorId or premixNo/stageType, depending on the approval scope
- motorSubmissionType and motorSubmissionStatus for a motor action
- premixSubmissionType and premixSubmissionStatus for a premix action
- divisionSubmissionType and divisionStatus for a division action
- unlockedDivision
- allDivisionsApproved and division counts
- allMotorsApproved and motor counts
- divisionStatuses, motorStatuses, premixStatuses, and divisionDetails
- created/submitted/approved audit fields

Fields that do not apply to the selected approval scope can be null or omitted.


LEGACY APPROVER ENDPOINTS
=========================

Premix:

POST /api/v1/approver/form/premix/change-status

For a QC Division form, include divisionId and division with the existing
premixNo, subType, and stageType fields.

Motor:

POST /api/v1/approver/form/motor/change-status

For a QC Division form, include divisionId and division with the existing
motorId and subType fields.


APPROVER VALIDATION ERRORS
==========================

The API rejects the request when:

- divisionId or division is missing.
- divisionId and division do not match.
- The division does not belong to the supplied QC form workflow.
- premixNo is missing for a premix division.
- motorId is supplied for a premix division.
- stageType is missing for MIXING.
- motorId is missing for a motor division.
- premixNo is supplied for a motor division.
- A unit identifier is supplied for a division-level approval.
- The selected division/unit is not waiting for approval.
- rejectionReason is missing for REJECTED.
- The selected division data or unit is not present in the QC form.

Representative error response:

{
  "success": false,
  "code": 400,
  "message": "divisionId 3 does not match division MIXING",
  "errorCode": "INVALID_REQUEST",
  "requestId": "<request-id>",
  "timestamp": "<timestamp>"
}


QC STRICT DTO CONTRACT - BRUNO REQUEST AND RESPONSE BODIES
===========================================================

This section matches commit 3581bec (qc dtos fixed). Use these bodies for
Bruno testing. The older create/update examples after this section are marked
obsolete because some of their field names pre-date the strict DTOs.


WHAT CHANGED IN COMMIT 3581bec
==============================

- CreateQcDivisionRequest.divisionDetails and
  UpdateQcDivisionRequest.divisionDetails changed from List<Map<String,Object>>
  to List<DivisionDetailInput>.
- DivisionDetailInput selects a fixed data DTO from division/subType.
- Unknown fields are rejected at division, division-data, section, process,
  premix, stage, and motor levels.
- DivisionDetailDto.data is now a typed DivisionDataResponse instead of a Map.
- Details responses now include submittedBy/submittedAt and
  approvedBy/approvedAt at division/unit level when those values exist.
- Request DTOs contain only client-owned fields. Do not copy backend-managed
  response fields into create/update requests.

Backend-managed fields rejected in a request include divisionId, status,
divisionSubmissionStatus, premixSubmissionStatus, motorSubmissionStatus,
remarks/rejectionReason used by approval, actionBy/actionAt, submittedBy,
submittedAt, approvedBy, and approvedAt.


BRUNO SETUP
===========

Method header for POST/PUT calls:

  Content-Type: application/json
  Authorization: Bearer {{accessToken}}

Suggested Bruno environment variables:

  baseUrl          Example: http://localhost:8080
  accessToken      Logged-in User token
  batchId          Existing active batch ID
  subDepartmentId Existing QC sub-department numeric ID
  formId           Set from the create response
  motorId          A motor ID that belongs to batchId

The sample IDs are placeholders. Replace BATCH-2026-001, QC-F-0001, and
MOTOR-001 with records that exist in the test database.


1. CREATE - ONE COMPLETE STRICT-DTO REQUEST
===========================================

Method: POST
URL: {{baseUrl}}/api/v1/user/qc-division/create

This body exercises every division DTO in one request. Only the initially
unlocked Raw Material Revalidation division has a submission action. The
remaining division objects are template data and intentionally omit their
submission-type field. To test later workflow actions, use the Update bodies
in section 3 after the preceding division is approved.

For source-backed motor divisions, the QC request now reuses the current
direct DTO body from that source department:

- HARDWARE uses Case Preparation motor fields (`motorId`,
  `abradingOperation`, `bellowBonding`, `tceCleaning`, `preHeating`,
  `linerCoatingOperation`, and `dispatchToCasting`). Do not send the legacy
  `motorIdNo` or `sections` array.
- CASTING and CURING use the direct Casting/Curing fields (`motorId`, setup
  objects, and named `castingSections`/`curingSections`). Do not send legacy
  QC casting blocks or a curing section array.
- DE_CORING uses `motorId` and the direct Casting/Curing `decoringDetails`
  object.
- POST_CURE uses the direct Post Cure motor fields, including the nested
  `epoxyPreparationIngredients` object.
- NDT uses `NdtMotorDto` fields. Do not send the legacy `processDetails`
  array.

Add `motorSubmissionType` (`DRAFT` or `SUBMIT`) to the motor being actioned.
The backend controls `motorSubmissionStatus` and all approval/audit fields.

WHERE SUBMISSION TYPES ARE SENT
===============================

1. RAW_MATERIAL_REVALIDATION and WEIGHTMENT

Add at divisionDetails item level:

  "divisionSubmissionType": "DRAFT"

or:

  "divisionSubmissionType": "SUBMIT"

2. RAW_MATERIAL_PROCESSING

Add inside the selected data.premixes item:

  "premixSubmissionType": "DRAFT"

or SUBMIT. Each premix has independent status.

3. MIXING

The payload remains one data.premixes item containing both nested detail
objects. Add premixSubmissionType inside the stage being saved:

{
  "premixNo": 1,
  "premixDetails": {
    "premixSubmissionType": "SUBMIT",
    "bowlNo": "PM-001",
    "parameters": []
  },
  "finalMixDetails": {
    "bowlNo": "FM-001",
    "parameters": [],
    "viscosityBuildUp": []
  }
}

Later, after PREMIX is approved, Final Mix can be submitted without changing
the outer structure:

{
  "premixNo": 1,
  "premixDetails": {
    "premixSubmissionType": "SUBMIT",
    "premixSubmissionStatus": "APPROVED",
    "bowlNo": "PM-001",
    "parameters": []
  },
  "finalMixDetails": {
    "premixSubmissionType": "SUBMIT",
    "bowlNo": "FM-001",
    "parameters": [],
    "viscosityBuildUp": []
  }
}

PREMIX and FINAL_MIX therefore keep separate premixSubmissionStatus values.
The Mixing division is APPROVED, and the next QC division is unlocked, only
when PREMIX and FINAL_MIX are approved for every configured premix number.

4. MOTOR-SCOPED DIVISIONS

Add motorSubmissionType inside each selected motor object. The exact array and
identifier keys remain division-specific:

Division                       Array key                  Identifier key
-----------------------------  -------------------------  --------------
HARDWARE                       motorDetails               motorIdNo
CASTING                        motorDetails               motorIdNo
CURING                         curingDetails              motorIdNo
DE_CORING                      deCoringDetails            motorIdNo
TRIMMING                       trimmingDetails            motorIdNo
POST_CURE_OPERATION/POST_CURE  postCureMotorDetails       motorIdNo
PROPELLANT_PROPERTIES          motors                     motorId
NDT                            motorDetails               motorId

Example:

{
  "motorIdNo": "MOTOR-001",
  "motorSubmissionType": "SUBMIT",
  "processDetails": {}
}

All motor IDs must belong to the batch. A motor division unlocks its successor
only after all configured batch motors are approved for that division.

For CURING, motorPositioningDateTime is supplied inside each curingDetails
object before curingSections. Use ISO local date-time format:
YYYY-MM-DDTHH:mm:ss (for example, 2026-06-20T08:00:00).

For TRIMMING, each trimmingDetails motor supports the complete source data:

- trimmingOperationDetails: rows from the Manufacturing Trimming
  TRIMMING_DETAILS section.
- trimmingMeasurementDetails: flattened rows from TRIMMING_COMMON_FORMAT.
- trimmingRemarks: an object containing business remarks and reportLink from
  TRIMMING_REMARKS. Keep these business remarks nested because motor-level
  remarks is reserved for the QC approval workflow.

Both Create and draft Update accept this same structure. QC details returns
the saved fields unchanged under divisionDetails[].data.trimmingDetails[].

PRE-STRICT VALIDATION NOTES (OBSOLETE)
======================================

- Create formSubmissionType must be DRAFT.
- Create fails when an active QC form already exists for the batch.
- Create/DRAFT Update requires at least one divisionDetails item; it may carry
  the complete form array.
- Division data is validated using its real collection and identity keys.

- Motor identifiers must belong to the batch.
- WAITING_FOR_APPROVAL and APPROVED units cannot be edited.
- Unchanged workflow fields returned by Details can be sent back during a
  complete payload update.
- Form-level SUBMIT is rejected because final completion is automatic.
- Unit-level submissionType remains DRAFT or SUBMIT as before.

QC CREATE, UPDATE, AND DETAILS APIs (OBSOLETE)
==============================================

GENERAL SAVE RULES
==================

- A QC form contains a sequential workflow of enabled QC divisions.
- Only the currently unlocked division can be created or updated.
- Every create or DRAFT update must contain exactly one divisionDetails item.
- That divisionDetails item must contain exactly one division-level action,
  one premix, or one motor.
- A division/unit submission type can be DRAFT or SUBMIT:
  - DRAFT produces IN_PROGRESS.
  - SUBMIT produces WAITING_FOR_APPROVAL.
- Entries in WAITING_FOR_APPROVAL or APPROVED status cannot be edited.
- Rejected entries can be corrected and submitted again.
- A final form SUBMIT is allowed only after all QC divisions are approved.

CREATE/UPDATE VALIDATION ERRORS
===============================

- Create formSubmissionType must be DRAFT.
- Create fails if a QC form already exists for the batch.
- formId, batchId, and subDepartmentId must identify the same form on update.
- Exactly one divisionDetails item and one unit are required for a DRAFT save.
- The selected division must be unlocked.
- data.sections is required for division-level data.
- data.premixes is required for premix divisions.
- data.motors is required for motor divisions.
- sectionId and sectionData are required for every section.
- premixNo must be valid for the batch.
- motorId must belong to the batch.
- Submission type must be DRAFT or SUBMIT.
- WAITING_FOR_APPROVAL and APPROVED entries cannot be modified.
- Final SUBMIT requires empty divisionDetails and all divisions approved.

direct camelCase DTO fields. Do not send formSections, sectionId, sectionData,
uppercase schema keys, or motorSubmissionStatus. Existing schema-shaped
documents in static_testings and bem_motors must be deleted and recreated.

RMP PREMIX APPROVAL AND BLOCKCHAIN ASSET (BRUNO)
================================================

Use this ACEM backend request to exercise the RMP approval flow. After ACEM
saves the approval, the microservice immediately attempts asset delivery and
retries failures on its schedule. A gateway outage does not undo the approval.

Method: POST
URL: {{acemBaseUrl}}/api/v1/approver/form/premix/change-status
Headers:
  Content-Type: application/json
  Authorization: Bearer {{approverToken}}

Request body:

{
  "formId": "RMPF-2026-0017",
  "premixNo": 1,
  "subDepartmentId": 3,
  "actionType": "APPROVED",
  "remarks": "Premix verified and approved"
}

Success response: 200 OK

{
  "success": true,
  "code": 200,
  "message": "Premix approved successfully",
  "data": {
    "formId": "RMPF-2026-0017",
    "batchId": "BATCH-2026-0042",
    "premixNo": 1,
    "actionType": "APPROVED",
    "status": "APPROVED",
    "premixSubmissionStatus": "APPROVED",
    "batchStatus": "WAITING_FOR_PARTIAL_APPROVAL",
    "allPremixesApproved": false,
    "pendingPremixCount": 1,
    "approvedPremixCount": 1,
    "rejectedPremixCount": 0,
    "totalPremixCount": 2,
    "remarks": "Premix verified and approved",
    "actionBy": "admin",
    "actionAt": "2026-09-30T12:00:00"
  },
  "timestamp": "2026-09-30T12:00:00"
}

Use a `formId` and `premixNo` currently waiting for approval. Set
`subDepartmentId` to 3 for raw material preparation. The corresponding asset
ID is `uid:acem:asset/{batchId}:{formId}/{premixNo}`. The gateway request and
response payload example is in `RAW_MATERIAL_PREPARATION_ASSET_API.txt`.
